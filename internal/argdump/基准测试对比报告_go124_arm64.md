## 基准测试对比报告（go1.24 + darwin/arm64）

### 目的

对比以下三类开销（以 `ns/op`、`B/op`、`allocs/op` 量化）：

- **unpatched**：原始函数调用基线
- **patched + NoDump**：仅 hook + 继续执行原函数（`argdump.DumpEnabled=false`）
- **patched + DumpToDevNull**：hook + dump（stdout 重定向到 `/dev/null`，仍会执行 `fmt.Printf` + `abijson` 编码）

### 基准测试代码

- `internal/argdump/bench_go124_arm64_test.go`

### 运行命令

```bash
cd /Users/jake/Documents/Projects/goom && /Users/jake/sdk/go1.24.10/bin/go test ./internal/argdump \
  -run '^$' \
  -bench '^(Benchmark_Unpatched_Add|Benchmark_Patched_Add_DumpToDevNull|Benchmark_Patched_Add_NoDump|Benchmark_Unpatched_MultiReturn|Benchmark_Patched_MultiReturn_DumpToDevNull|Benchmark_Patched_MultiReturn_NoDump)$' \
  -benchmem \
  -count=7
```

### 运行环境

- **goos**: darwin
- **goarch**: arm64
- **cpu**: Apple M1 Max

### 结论（要点）

- **NoDump** 仍有 **80B / 4 allocs/op**：这反映的是 hook/reflect 路径自身的分配，而不是打印/JSON 编码。
- **DumpToDevNull** 的额外成本主要来自 **fmt.Printf + abijson 编码 + 字符串处理**（即便 stdout 指向 `/dev/null`）。
- `Benchmark_Patched_Add_DumpToDevNull` 在 7 次运行中出现了 **两次明显更低的 ns/op（~3.16µs）**，其余集中在 ~10.4–10.6µs；建议后续如需更严谨结论，可进一步提高 `-count`，并用 `benchstat` 做统计比较。
