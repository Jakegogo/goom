## 背景与目标

当前 `argdump` 已在 **go1.24 + arm64** 路径跑通（基于 `reflect.makeFuncStub` + 替换 `reflect.callReflect` + `PatchFunc` 入口 patch）。接下来需要扩展到：

- **架构**：`amd64`、`386`（并保持 `arm64`）
- **Go 版本**：从 **go1.13** 到 Go 最新版本

核心目标保持不变：

- **不使用 `reflect.Value` 处理参数/返回值**（dump 依赖 `reflect.Type + unsafe.Pointer`）
- **Patch 任意函数**：dump 入参/返回值后继续执行原函数（可选 trampoline 或 fallback）
- **尽量稳定、低侵入**：兼容 runtime/GC/ABI 变化，并在无法安全 trampoline 时自动降级

---

## 总体架构（分层）

### Layer 0：公共 API（不分架构/版本）

- `MakeDumpFunc(typ reflect.Type) any`：生成与 `typ` 动态类型一致的 dump func（只打印，不调用原函数）
- `PatchFunc(fn any) (*patch.Guard, error)`：patch 函数入口，dump 后继续执行原函数
- `PatchFuncPtr(originPC uintptr, funcVal unsafe.Pointer, typ reflect.Type)`：底层入口

### Layer 1：Go 版本/架构绑定层（build tags）

需要按 **Go 版本段** 与 **架构** 拆分实现文件（见下方“代码组织”）。

这一层负责：

- `reflect.makeFuncStub` / `reflect.callReflect` 的定位与替换策略
- `runtime.reflectcall` 的 linkname 声明（签名/参数含义随版本差异）
- 参数/返回值 ABI 描述（寄存器/栈布局）与 `RegArgs` 结构（不同版本/架构不同）
- arm64e/PAC 等平台特性的规避（跳转策略）

### Layer 2：patch/trampoline 基础设施（internal/patch）

复用现有 `internal/patch`：

- 入口 patch（各 arch 不同指令编码）
- trampoline 构建（拷贝 origin prologue、修复 PC-relative、跳回 origin+N）
- fallback：无法 trampoline 或 closure/methodvalue 时，使用 Unpatch/Restore 方案

---

## 关键技术点（必须解决的问题）

### 1) `reflect.MakeFunc` 的桥接机制（跨签名接参）

我们复用 stdlib 的 `reflect.makeFuncStub`，它把调用现场拆成：

- **寄存器参数** → `runtime.spillArgs` spill 到 `RegArgs`
- **栈参数/返回区** → `argframe` 指针作为 `frame`
- 调用 `callReflect(ctxt, frame, &retValid, &RegArgs)`（我们替换为 `callDump`）

因此 `callDump` 能在不依赖 Go 源码签名的情况下读取任意 `typ` 的参数与返回值。

### 2) 为什么必须替换 `reflect.callReflect`（避免 `reflect.Value`）

stdlib 的 `callReflect` 会构造 `[]reflect.Value`，违背“不使用 reflect.Value 处理参数”的约束。

方案：

- 仍复用 `reflect.makeFuncStub`（runtime/GC stack map 特殊处理）
- 但将 `reflect.callReflect` 整体替换为 `argdump.callDump`：
  - **命中 magic**：走 dump（以及 PatchFunc 的 “dump → 调原函数 → dump ret”）
  - **未命中**：转发到原始 `callReflect`（trampoline 保存）

### 3) ABI/寄存器传参差异（go1.13～go1.16 vs go1.17+）

这是跨版本的最大差异点：

- **go1.13～go1.16**：没有 ABIInternal 的“寄存器优先”新 ABI；多数平台调用约定更偏栈传参，`RegArgs`/spill 机制不同（甚至不存在同形态结构）。
- **go1.17+**：引入 ABIInternal，参数优先走寄存器；`abi.RegArgs`、`spillArgs/unspillArgs` 成为关键。

因此需要按版本段实现：

- `go1.13-1.16`：以 **栈参数帧**为主（frame-only）；寄存器部分视具体版本/arch 决定是否支持或做降级。
- `go1.17+`：frame + regargs 双通路；准确维护 ReturnIsPtr 等 GC 可见性。

### 4) PatchFunc “继续执行原函数”的两种策略

#### A) trampoline（推荐，低抖动）(优先选)

- patch 时构造 `fixOriginPtr`：拷贝 origin prologue 并修复 PC-relative，然后跳回 origin+N
- hook 内 `runtime.reflectcall` 调用 `fixOriginPtr`（不会再次进入 hook，无需 Unpatch/Restore）

限制：

- 若 origin 内部存在分支跳回被覆盖的 prologue（例如 “branch jumps into the first N bytes”），trampoline 不安全，需要 fallback
- closure/method value 有 context：trampoline 调用需要正确 ctxt，无法通用合成，通常 fallback

#### B) Unpatch/Restore（fallback，通用但有窗口）

- hook 内先 `UnpatchWithLock()`（写回 originBytes）
- `runtime.reflectcall` 调原函数
- `Restore()`（重新写入 jumpBytes）

注意：`Guard.Restore()` 的语义是 **重新 patch**，不是恢复原字节。

## 代码组织（建议目录与 build tags）

### 1) `internal/argdump` 代码拆分

建议按 **版本段 × 架构** 拆：

- `dumpfunc_go1xx_arm64.go` / `dumpfunc_go1xx_amd64.go` / `dumpfunc_go1xx_386.go`
- `patchfunc_go1xx_arm64.go` / ...
- `abi_desc_go1xx_arm64.go` / ...
- `rtiface_go1xx_arm64.go` / ...（runtime/reflect 内部结构镜像：rtype/funcval/RegArgs 等）

并在文件头用 build tags 控制：

- `//go:build go1.24 && arm64`
- `//go:build go1.20 && amd64`（示例）
- `//go:build go1.13 && 386`（示例）

**版本段建议**（更可维护）：

- `go1.13-1.16`：`go1.13 && !go1.17`
- `go1.17-1.20`：`go1.17 && !go1.21`
- `go1.21-1.23`：`go1.21 && !go1.24`
- `go1.24+`：`go1.24`

> 具体分段可根据实际差异调整；分段越少越好，但必须覆盖 ABI/reflectcall/RegArgs 变化点。

### 2) `internal/patch` 的架构拆分与复用

- `monkey_{arch}.go`：通用 patch 的跳转生成（历史代码）
- `ptr_jump_{arch}.go`：需要设置 CTXT、并提供 trampoline 入口的专用 patch API
- `fix_origin_{arch}.go`：trampoline 构建（copy+reloc+return）
- `fix_addr_{arch}.go`：PC-relative 指令重定位

注意：不同架构的“短跳/长跳”策略不同：

- `arm64`：`B imm26` ±128MB；超范围 `MOV x16; BR x16`
- `amd64`：可用 `JMP rel32` 或 `MOV rax, imm64; JMP rax`
- `386`：可用 `JMP rel32` 或 `MOV eax, imm32; JMP eax`（受地址空间限制）

## 兼容性矩阵（建议逐步推进）

为降低一次性支持所有组合的风险，建议按“控制变量法”推进：

### Phase 1：go1.17+ 优先（ABIInternal，RegArgs 清晰）

- `amd64`：优先实现
- `arm64`：已完成 go1.24，向低版本回补
- `386`：实现 stack-only + 逐步补寄存器路径（如果该版本/架构存在等价结构）

### Phase 2：go1.13-1.16（老 ABI）

策略建议：

- 先支持 `MakeDumpFunc + PatchFunc` 的 **stack-only** dump（frame-only）
- `PatchFunc` 继续执行原函数优先用 trampoline；不稳定时 fallback Unpatch/Restore
- 如遇到没有 `RegArgs` 或 `spillArgs` 机制，`callDump` 的签名/参数也需按该版本 stdlib 调整

## 测试策略（全方位验证）

### 1) 单元测试覆盖维度

按架构/版本分别跑（build tags 分发）：

- 参数类型覆盖：
  - ints/uints/bools
  - floats（验证 float regs）
  - pointers（*T）、interfaces、maps/slices/arrays
  - structs（含未导出字段 + MaxDepth=3）
  - variadic（验证 `[]T` materialize）
  - closures（捕获变量）
  - panic（panic dump + patch 仍保持激活）
- 返回值覆盖：
  - 多返回值（含 float）
  - 指针返回（ReturnIsPtr/GC 可见性）

### 2) 关键不变量断言

- Patch 后函数返回值保持正确
- dump 输出包含关键字段（argN/retN/panic）
- trampoline 模式下：不发生递归，不需要 Unpatch/Restore
- fallback 模式下：panic 也会 Restore（重新 patch）

---

## 风险与降级策略

- **trampoline 重定位复杂度**：不同架构的 PC-relative 指令集差异大；当发现“branch into prologue”等不可修复形态时，必须自动 fallback
- **arm64e/PAC**：避免 “从内存加载 code pointer 再间接跳转”（已通过统一跳转策略解决）
- **go1.13-1.16 ABI 差异**：可能需要接受“部分场景只支持 dump，不支持继续执行”作为阶段性目标（或仅 fallback）
